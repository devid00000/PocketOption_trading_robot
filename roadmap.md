### Где остановились

На проверке совпадения свечей `DebugChartWindow` с графиком Pocket Option. История загружается, но визуально отличается от платформы: цвета, размеры тел/теней и в отдельных случаях цены не совпадают. Источник расхождения установлен частично: методы API библиотеки в версии `0.2.14` не всегда используют одну и ту же ценовую серию.

### Текущее рабочее решение и ограничения

- Баланс: `balance()` через один worker-owned asyncio loop.
- Активы: `active_assets()`, в графике оставлены только `asset_type == "currency"`.
- История: `compile_candles()` с последними 50 свечами.
- Realtime: текущая реализация использует polling того же OHLC endpoint, чтобы не смешивать несовместимые raw/timed источники.
- `get_candles_live()` напрямую не используется: на установленной версии он падает внутри библиотеки из-за `None` в одном из history fallback-методов.
- Браузер после перехвата SSID закрывается; котировки из браузера пока не подключены.

### Следующий технический шаг

1. Оставить Playwright browser context открытым после авторизации.
2. Перехватить и классифицировать WebSocket frames платформы без вывода секретов.
3. Найти поток, из которого строится именно видимый платформенный график.
4. Сравнить 5-10 закрытых баров по `timestamp/open/high/low/close` с Python-графиком.
5. Только после совпадения OHLC стабилизировать renderer и продолжить этап 2.

### Безопасность checkpoint

- `.env` и локальные credential-файлы не должны попадать в GitHub.
- Старые SSID из предыдущих версий следует считать скомпрометированными.
- До совпадения OHLC и завершения этапов 3-5 не выполнять real-сделки и не включать автоторговлю.

## 1. Резюме

Проект представляет собой не завершённый торговый терминал, а набор связанных прототипов разной степени готовности. Архитектура ближе к слоистой (`ui` -> `core`/`strategies` -> `storage`/неофициальный API), но строгого MVC/MVVM нет: GUI напрямую создаёт движок, управляет потоками и вызывает торговые методы.

Главный положительный результат: базовые модели, программно созданный PySide6 GUI, реестр индикаторов, JSON-сериализация и SQLite-хранилище уже дают основу для продолжения. Главный технический долг: необходимо сначала стабилизировать единый API-клиент и модель конкурентности, потому что текущий код вызывает один `PocketOptionAsync` из разных event loop и использует одновременно рабочий `subscribe_symbol_timed()` и заведомо таймаутящий `subscribe_symbol()`.

Заявление README о полностью рабочей системе не подтверждается кодом. Реально готова часть каркаса и отдельные локальные компоненты; подключение, торговля, история и запуск роботов требуют переработки и интеграционных проверок на демо-счёте.

## 4. Критические технические проблемы

### P0: безопасность и реальные деньги

- До этапа 0 действующие или похожие на действующие SSID/сессии были захардкожены во многих `.py` и документации. На этапе 0 они удалены из проектного кода и тестовых скриптов; старые значения следует считать скомпрометированными и отозвать/обновить. Локальный `.env` очищен от прежнего значения.
- `.env` содержит session cookie. Файл должен быть исключён из контроля версий, права доступа должны быть ограничены; в логах нельзя печатать SSID. Сейчас `RobotEngine.connect()` выводит первые 60 символов (`core/robot_engine.py:106-108`).
- До завершения этапов 1-5 торговля должна быть разрешена только на demo по умолчанию. Для real необходимы явный выбор, повторное подтверждение и визуальный индикатор режима.

### P0: async/threading

- `RobotWorker` владеет event loop в `QThread`, но GUI планирует корутины через event loop GUI-потока (`ui/app.py:808-814`), а не через `worker._loop`. Подписка может не выполниться или выполниться в неправильном loop.
- Developer panel создаёт новый `threading.Thread` и новый event loop, затем использует клиент, созданный в loop `RobotWorker` (`ui/widgets/developer_panel.py:502-525`). Это нарушение loop affinity WebSocket-клиента и источник случайных ошибок/зависаний.
- `RobotWorker.stop()` вызывает `loop.stop()` во время `run_until_complete`, что может привести к `RuntimeError: Event loop stopped before Future completed` и не гарантирует корректный `disconnect()` (`ui/app.py:114-119`).
- Callback `_on_disconnected` вызывается только через `await`, в то время как остальные callbacks частично поддерживают sync/async; контракт непоследователен (`core/robot_engine.py:158-160`).

### P0: поток котировок и результаты сделок

- `subscribe()` немедленно запускает `subscribe_symbol()` (`core/robot_engine.py:355-357`, `core/robot_engine.py:393-407`), который согласно `test_quotes/RESULTS.md` таймаутит.
- Параллельный `_candle_stream_loop` должен запускать `subscribe_symbol_timed()`, но не делает этого, если ключ уже находится в `_candle_tasks`; его заняла задача `subscribe_symbol()`. В результате рабочий способ подписки блокируется нерабочим.
- Успешная подписка не гарантируется: `_start_candle_stream()` поглощает исключение, а `subscribe()` всё равно возвращает `True`.
- Проверка закрытия сделки вызывает `get_candles()` (`core/robot_engine.py:539-558`), хотя собственные результаты исследования помечают этот метод как таймаутящий. Это способно навсегда задержать обработку pending deals.
- При любой ошибке определения цены сделка принудительно помечается проигрышной (`core/robot_engine.py:585-593`), что создаёт ложную историю и неверные решения мартингейла.
- Выплата жёстко задана как 92%, игнорируется payout конкретного актива (`core/robot_engine.py:565-584`).
- Локальный баланс вручную уменьшается на ставку после открытия (`core/robot_engine.py:680-687`), хотя серверный баланс обновляется отдельно. Это вызывает временные двойные/ложные значения.

### P1: точки входа и конфигурация

- `main.py` и README ссылаются на отсутствующие модули и файлы: `ui.gui_app`, `test_trading_bot`, `get_session_cookie.py`.
- До этапа 0 `run_gui.py`, `main.py`, `config/settings.py` и локальные шаблоны использовали разные имена переменных. На этапе 0 введён канонический runtime-конфиг с ограниченным fallback для старых имён; шаблон `.env.example` удалён как неиспользуемый.
- `BinaryOptionsToolsV2` не указан в `requirements.txt`; установка описана только текстом и привязана к wheel для Linux x86_64.
- `config/settings.py` почти нигде не используется; `config/api_config.json` и его список активов тоже не являются источником истины.
- Пути `robots`, `storage/trades.db`, `strategies/configs` зависят от текущей рабочей директории, что уже привело к двум файлам базы.

### P1: модели и стратегии

- Одновременно существуют `core/strategies/base.py` и `strategies/base.py` с разными интерфейсами и шкалами сигналов.
- Одновременно существуют `TechnicalIndicators` и классы-обёртки индикаторов с дублирующими формулами.
- `RobotConfig` сохраняет новый формат, но при загрузке старого JSON игнорирует поле `strategy`, поэтому старые стратегии теряют настройки (`core/models.py:175-217`).
- При редактировании старого `RobotConfig` поля старого формата меняются, но созданный в `__post_init__` `strategy_config` не синхронизируется.
- `StrategyConfig.to_dict()` сохраняет индикаторы в структуре с `settings`, а название метода/комментарии смешивают внутренний и extension-форматы. В проекте существуют как минимум три несовместимых JSON-схемы.
- Новый `StrategyExecutor` не подключён к `RobotEngine`, GUI или хранению сделок. `start_trade_series()` игнорирует переданные direction/amount/duration.
- `timezone` хранится в регламенте, но `_check_regulations()` использует локальное `datetime.now()` (`strategies/strategy_executor.py:295-330`).
- `min_profit`, `time_inspection`, отдельный timeframe индикатора, лимиты сделок/дня и веса фактически не соблюдаются полностью.

### P1: GUI и хранилище

- История в главном окне отсутствует, а developer panel отображает только сделки текущей сессии.
- `TradeLogger` нигде не вызывается из движка.
- CSV формируется простым `','.join`, поэтому значения с запятыми/кавычками будут повреждены (`storage/trade_logger.py:526-548`).
- `INSERT OR REPLACE` при открытии сделки может удалить существующую строку и заново создать её, потеряв поля закрытия.
- Логгер пишет в каталог уровнем выше корня проекта (`utils/logger.py:34`), а README указывает другие пути.
- В `TradingTab` дважды вызывается `setLayout()` для группы логов, из-за чего layout кнопки очистки теряется (`ui/widgets/trading_tab.py:422-445`).
- Developer panel вызывает `self.log()` из обычного Python-потока, что небезопасно для Qt.

## 5. Целевая архитектура

Рекомендуемая минимальная архитектура без избыточного фреймворка:

```text
PySide6 UI
  -> ApplicationController / Qt signals
    -> PocketOptionService (единственный asyncio loop в одном QThread)
      -> BinaryOptionsToolsV2 adapter
    -> MarketDataService (нормализация и кэш свечей)
    -> TradeService (команды, открытые/закрытые сделки)
    -> StrategyRuntime (сигналы, лимиты, мартингейл)
    -> Repositories (SQLite, JSON settings/history)
```

Обязательные правила:

- Один экземпляр клиента принадлежит одному event loop и одному worker-потоку.
- GUI взаимодействует с worker только Qt-сигналами и thread-safe command queue/`run_coroutine_threadsafe`.
- Все API-ответы преобразуются в внутренние dataclass-модели в адаптере.
- Время внутри приложения хранится в timezone-aware UTC; локальная зона используется только для отображения.
- Demo является режимом по умолчанию; real включается явно.
- Ни SSID, ни cookies не попадают в код и логи.
- Сначала поддерживается проверенный контракт конкретной версии `BinaryOptionsToolsV2`; неподтверждённые методы изолируются capability flags.

## 6. Дорожная карта

Оценка дана как ориентир по числу затрагиваемых файлов и ключевых функций, а не календарный срок. После каждого этапа предусмотрена ручная приёмка на demo-счёте.

### Этап 0. Стабилизация основы и воспроизводимого запуска

**Цель:** устранить блокирующие архитектурные и конфигурационные расхождения до добавления функций.

**Ожидаемый результат:**

- Одна рабочая точка входа для GUI.
- Единая схема переменных окружения и путей приложения.
- Зафиксированная совместимая версия `BinaryOptionsToolsV2` и инструкция установки.
- Удалены SSID из исходников и документации, добавлены безопасные шаблоны.
- Выбрана одна система стратегий; legacy-код изолирован или удалён после подтверждения миграции JSON.
- Минимальные unit/smoke тесты запускаются одной командой.

**Зависимости:** нет.

**Объём:** 8-12 файлов, 15-25 функций/настроек, 6-10 тестов.

**Критерии приёмки:** `main.py gui` открывает окно без сети; конфигурация загружается из одного места; тесты моделей/JSON/SQLite проходят; в проекте нет реальных SSID.

### Этап 1. Подключение и управление учётными записями

**Цель:** безопасно и предсказуемо подключать demo и real аккаунты.

**Ожидаемый результат:**

- Диалог «Параметры подключения» с URL, demo SSID, real SSID и состоянием валидности.
- Ручная запись параметров в `.env` с атомарным обновлением и маскированием секретов в UI.
- Кнопка браузерной авторизации. Сначала реализовать устойчивый полуавтоматический сценарий: открыть браузер, пользователь входит, приложение ожидает SSID через Playwright network/WebSocket inspection; если перехват невозможен, показать точную ручную инструкцию.
- Выбор Demo/Real, пересоздание соединения при переключении, обновление баланса и явная маркировка режима.
- Таймауты, отмена подключения, контролируемое отключение и reconnect с backoff.
- Проверка формата SSID до попытки подключения; URL не передаётся в библиотеку, если её API этого не поддерживает.

**Зависимости:** этап 0.

**Объём:** 5-8 файлов, 12-20 функций/слотов, 6-10 тестов.

**Критерии приёмки:** demo подключается и показывает баланс; неверный/просроченный SSID даёт понятную ошибку; real не включается случайно; секрет не виден в логах.

### Этап 2. DebugChartWindow, активы и realtime-график

**Цель:** создать изолированный стенд рыночных данных до интеграции в терминал.

**Ожидаемый результат:**

- Отдельное окно `DebugChartWindow` на PyQtGraph.
- Активы загружаются через `active_assets()`; статический список используется только как fallback с пометкой stale.
- Выбор S5, S10, S15, S30, M1, M5, M15, H1 и только разрешённых API периодов.
- Единственная подписка через `subscribe_symbol_timed()` с корректной отменой при смене актива/таймфрейма.
- История формируется из локального кэша realtime-свечей; отдельно исследуется безопасный bootstrap истории. `get_candles()` не используется без подтверждения на выбранной версии API.
- Эффективный candlestick item без полного `plot.clear()` на каждом тике.
- Отображение server time, UTC/local time, статуса потока и reconnect.

**Зависимости:** этапы 0-1.

**Объём:** 6-9 файлов, 18-28 функций, 8-12 тестов агрегации/кэша.

**Критерии приёмки:** график непрерывно обновляется минимум 30 минут, смена актива не оставляет старых задач, отключение сети приводит к восстановлению без зависания GUI.

### Этап 3. Ручные сделки CALL/PUT в окне отладки

**Цель:** подтвердить безопасный end-to-end торговый контракт на demo.

**Ожидаемый результат:**

- Поля суммы и экспирации с валидацией min/max для выбранного актива.
- CALL/PUT отправляются в worker loop через единый command API.
- Кнопки блокируются на время отправки, исключая двойной клик.
- Ответ API нормализуется в `Deal`; показываются trade ID и подтверждение.
- Результат берётся прежде всего из `closed_deals()`/подтверждённого API-контракта, а не вычисляется по приблизительной свече.
- Ошибка/таймаут не превращаются в проигрыш: используется статус `unknown` с возможностью повторной синхронизации.
- Для real требуется дополнительное подтверждение суммы и режима.

**Зависимости:** этапы 1-2.

**Объём:** 4-7 файлов, 12-20 функций, 8-12 тестов с mock adapter.

**Критерии приёмки:** на demo открываются CALL и PUT, обе появляются в API открытых сделках и затем получают серверный результат.

### Этап 4. Открытые сделки

**Цель:** показывать серверное состояние открытых позиций, а не только локальные команды.

**Ожидаемый результат:**

- Отдельная таблица открытых сделок с колонками: ID, актив, направление, вход, сумма, открытие, экспирация, оставшееся время, статус.
- Обновление событием и резервным polling с настраиваемым интервалом.
- Сверка локальных и серверных сделок после reconnect.
- Кнопка «Обновить»; «Закрыть» отображается только при подтверждённой поддержке API и требует подтверждения.
- Ошибки одной записи не ломают обновление всей таблицы.

**Зависимости:** этап 3.

**Объём:** 4-6 файлов, 10-16 функций, 5-8 тестов.

**Критерии приёмки:** открытая вручную сделка появляется в таблице, таймер экспирации корректен, после закрытия строка исчезает и переходит в историю.

### Этап 5. История закрытых сделок и экспорт

**Цель:** создать достоверный журнал сделок для анализа.

**Ожидаемый результат:**

- Таблица истории с активом, направлением, входом, выходом, суммой, payout, P/L, временем закрытия и источником результата.
- Зелёная/красная/нейтральная окраска без потери читаемости.
- Синхронизация `closed_deals()` с SQLite через repository/upsert без разрушения полей.
- Экспорт CSV через модуль `csv` и экспорт JSON; имя файла содержит UTC timestamp.
- Опциональный импорт JSON с валидацией схемы и защитой от дублей.
- Единый путь базы данных и простая версия схемы/миграция.

**Зависимости:** этапы 3-4.

**Объём:** 5-8 файлов, 15-24 функции, 10-15 тестов.

**Критерии приёмки:** история сохраняется после перезапуска; экспорт открывается корректно при запятых/Unicode; итоги совпадают с сервером.

### Этап 6. Конструктор и запуск стратегий

**Цель:** превратить существующий редактор JSON в работающий, контролируемый runtime роботов.

**Ожидаемый результат:**

- Одна версия моделей `StrategyConfig` и JSON Schema с номером версии и миграциями старых файлов.
- Конструктор условий без произвольного `eval`: AST/DSL с ограниченным набором операторов.
- Выбор SMA, EMA, RSI и MACD на первом проходе; затем Bollinger/Stochastic/CCI.
- Проверка min agreement, весов, времени, timezone, payout, лимитов, cooldown и числа открытых сделок.
- Background runtime работает в том же сервисном loop, не создаёт отдельные WebSocket-клиенты на каждого робота.
- Состояния робота: stopped, starting, running, paused, error.
- Dry-run/signal-only режим обязателен до разрешения автоторговли.
- Журнал сигналов и объяснение причин решения.

**Зависимости:** этапы 2-5.

**Объём:** 10-15 файлов, 30-50 функций, 25-40 тестов.

**Критерии приёмки:** импортированная стратегия генерирует воспроизводимые сигналы; dry-run не совершает сделок; demo robot соблюдает лимиты и восстанавливает состояние после reconnect.

### Этап 7. Индикаторы на графике и расширяемость

**Цель:** предоставить единый вычислительный и визуальный механизм индикаторов.

**Ожидаемый результат:**

- Единый реестр метаданных, вычисления и renderer factory.
- Добавление/удаление индикатора с периодом, источником цены, цветом, толщиной и pane/overlay.
- Пересчёт только затронутого хвоста данных при новой свече.
- SMA/EMA/Bollinger поверх цены; RSI/MACD в отдельных панелях.
- Сверка формул с эталонными наборами данных.
- Плагинный API допускается после стабилизации встроенных индикаторов: версия интерфейса, валидация и доверенная локальная директория. Не загружать произвольный код из импортируемого JSON.

**Зависимости:** этапы 2 и 6.

**Объём:** 8-12 файлов, 20-35 функций, 20-30 тестов.

**Критерии приёмки:** индикаторы визуально синхронны со свечами, параметры сохраняются, расчёты не замораживают GUI.

### Этап 8. Надёжность, наблюдаемость и безопасность

**Цель:** подготовить терминал к длительным demo-сессиям и контролируемому real-режиму.

**Ожидаемый результат:**

**Зависимости:** этапы 1-7; часть логирования выполняется раньше.

**Объём:** 6-10 файлов, 15-25 функций, 10-20 тестов.

**Критерии приёмки:** 8-часовой demo soak test без утечек задач/памяти; emergency stop прекращает новые сделки; секреты отсутствуют в логах.

## 7. Рекомендуемый порядок реализации

1. Утвердить этот roadmap и решить судьбу старых JSON/legacy-стратегий.
2. Выполнить этап 0 отдельным коротким циклом, иначе этап 1 будет строиться поверх сломанных точек входа и конфликтующих настроек.
3. Реализовать этап 1 только с безопасным demo-default и одним worker loop.
4. Использовать этапы 2-3 как интеграционный стенд API до переноса функций в главное окно.
5. После подтверждения серверных форматов сделок выполнить этапы 4-5.
6. Только после достоверной истории и лимитов включать runtime стратегий.

## 8. Основные риски

| Риск | Вероятность | Влияние | Снижение риска |
|---|---|---|---|
| Изменение неофициального API/Socket.IO | Высокая | Критическое | Адаптер, pin версии, contract tests, capability detection |
| Истечение/бан SSID | Высокая | Высокое | Явная диагностика, безопасное обновление, reconnect без бесконечного retry |
| Binary wheel доступен не для всех ОС/архитектур | Высокая | Высокое | Матрица поддержки, проверка установки до упаковки |
| Таймауты истории свечей | Высокая | Высокое | Realtime cache, локальное хранение, отдельное исследование bootstrap |
| Неверное определение результата сделки | Средняя/высокая | Критическое | Серверный источник истины, статус unknown, reconciliation |
| Ошибки event loop/thread affinity | Высокая в текущем коде | Критическое | Один loop-владелец клиента, очередь команд, Qt signals |
| Часовые пояса и переход через полночь/DST | Средняя | Высокое | UTC внутри, `zoneinfo`, server time sync, тесты |
| Потеря денег в real mode | Средняя | Критическое | Demo-default, подтверждения, hard limits, emergency stop |
| Несовместимые JSON-схемы | Высокая | Среднее | Версионирование и миграции, сохранение оригиналов |
| Произвольный код/выражения стратегий | Средняя | Высокое | Безопасный DSL/AST, запрет code plugins из JSON |

## 9. Решения, требующие утверждения

- Рекомендуется сохранить поддержку существующих JSON через одноразовые миграции, но не продолжать две параллельные модели стратегий.
- Рекомендуется сделать `run_gui.py` временной совместимой обёрткой, а `main.py gui` единственной документированной точкой запуска.
- Рекомендуется сначала реализовать Playwright-перехват SSID как экспериментальную возможность с ручным fallback: структура WebSocket auth может меняться, а cookie платформы не обязательно содержит полный SSID payload.
- Рекомендуется считать `closed_deals()` источником истины результата; сравнение общего баланса допустимо только как диагностический fallback, так как параллельные сделки/начисления делают разницу неоднозначной.
- Рекомендуется не включать real mode и автоторговлю до завершения этапов 1-5 и базовых hard limits этапа 8.

## 10. Ограничения текущего аудита

- Сетевые тесты не запускались, чтобы не использовать найденные секреты и не совершать действия на аккаунте.
- Выводы о ранее рабочих методах основаны на сохранённых результатах `test_quotes/RESULTS.md`; их потребуется повторно подтвердить новым demo SSID и зафиксированной версией библиотеки.
- `pytest` отсутствует в текущей `.venv`, поэтому автоматической тестовой коллекции нет. Имеющиеся файлы `test_quotes/test_*.py` являются ручными интеграционными скриптами и могут выполнять сетевые/торговые действия.
